# 什么情况下 workflow 已经够用，不需要 Agent

## 问题

什么情况下 workflow 已经够用，不需要 Agent？

## 状态

2. 已整理

## 为什么重要

很多 Agent 设计的问题，不是能力不够，而是起点就选错了。原本可以用清晰流程解决的任务，硬做成 Agent，常见结果是：

1. 成本更高
2. 调试更难
3. 结果更不稳定

所以这个问题本质上是在回答：什么时候应该克制，而不是继续加“自主性”。

## 短答案

当任务目标明确、步骤大体可预见、输入输出结构相对稳定、工具选择范围有限、失败后需要确定性回退时，workflow 往往已经够用，不需要 Agent。

只有当下一步行动强依赖中间观察，且环境不确定、信息不完整、固定分支难以覆盖时，Agent 的价值才会开始变得明显。

## 展开说明

workflow 更适合下面几类场景：

1. 任务可以被拆成稳定步骤，比如抓取、清洗、分类、汇总。
2. 分支虽然存在，但大部分都能预先枚举。
3. 工具使用顺序基本固定，不需要模型临场选择很多路径。
4. 失败成本较高，需要清晰日志、确定性回退和强约束。
5. 任务会重复执行，流程复用价值高。

Agent 更值得考虑的场景通常有这些特点：

1. 信息要边查边补，无法一开始就拿到完整上下文。
2. 中间发现会显著改变后续路径。
3. 同一个目标可能存在多种可行策略，且很难提前写死。
4. 任务的探索成本低于错误自动化的代价。

一个很实用的工程取舍是：先从 workflow 起步，只把最不确定、最依赖模型临场判断的那一小段做成 agentic 节点。

这通常比“整条链路全部 Agent 化”更容易调试，也更容易验证收益来自哪里。

## 常见误区

1. 输出是开放式文本，就一定需要 Agent。
2. workflow 效果不理想，就应该马上增加自主决策。
3. 只要任务复杂，Agent 一定比 workflow 更强。
4. 把 demo 阶段的灵活性，误当成长期维护阶段的稳定收益。

3. 任务复杂度提升到什么程度后，固定流程的维护成本会反超 Agent。
