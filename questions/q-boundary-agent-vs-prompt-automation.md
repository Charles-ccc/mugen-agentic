# Agent 和普通 prompt automation 的边界在哪里

## 问题

Agent 和普通 prompt automation 的边界在哪里？

## 状态

2. 已整理

## 为什么重要

如果边界不清，团队很容易把任何“用了模型、串了几步、调了几个工具”的系统都叫成 Agent。结果通常是两个问题：

1. 设计被过度复杂化
2. 评估口径变得混乱，最后连失败原因都说不清

## 短答案

边界不在“有没有用大模型”，也不在“有没有工具调用”，而在系统是否需要在不确定环境中形成观察、决策、行动、再观察的闭环，并根据中间反馈主动调整后续动作。

如果流程基本固定、分支已知、失败处理写死，那么它更接近 prompt automation 或 workflow，而不是 Agent。

## 展开说明

可以先用三个层次区分：

1. Prompt automation：通常是一轮生成，或一组固定步骤的串联。即使有多步，也主要是预先定义好的处理流程。
2. Workflow：存在明确编排、固定节点和已知分支，模型只是其中一个执行单元。
3. Agent：系统需要根据中间观察决定下一步做什么，往往还要维护状态、调用工具，并在结果不理想时改变策略。

一个实用判断标准是看“中间反馈是否真的改变后续行为”。

如果把中间观察结果换掉，系统的后续动作依然几乎不变，那么它大概率不是 Agent，只是一个带模型的流程。

另一个实用判断标准是看“决策自由度是否真实存在”。

如果工具选择、执行顺序、失败回退几乎都被预先写死，那么系统虽然看起来有多步推理，但本质上仍然偏 workflow。

在真实工程里，这不是一个非黑即白的分类，而更像一条连续光谱。很多实用系统不是“纯 Agent”，而是“workflow 外壳 + 局部 agentic 决策”。

## 常见误区

1. 只要会调用工具，就是 Agent。
2. 只要有多轮对话，就是 Agent。
3. 只要加了 planning 或 ReAct prompt，就天然比 workflow 更高级。
4. 把“看起来更自主”误当成“更适合生产环境”。
